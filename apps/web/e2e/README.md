# Web E2E (Playwright, Chromium)

Run `pnpm e2e` from the repository root (or `pnpm --filter @salesforce/web run e2e`); the first time on a machine, run `pnpm --filter @salesforce/web run e2e:install` once to download Chromium (a download, not an install script). The suite needs Docker running and starts its own throwaway stack: a `postgres:17` container without volume (`sf-e2e-postgres-55498`, 127.0.0.1:55498), the repository's real `db:migrate`, `db:queue:install`, `db:seed` and one `sync:once` against the fake Sankhya gateway, the API on 127.0.0.1:3100 and the Vite dev server on 127.0.0.1:5273, and removes all of it when the run ends. Passwords are random per run and never written to disk; no `.env` is read or written. It refuses to start on the developer stack's ports (3000, 3001, 5173, 4173, 55432) and never reuses a busy port: override with `E2E_PG_PORT`, `E2E_API_PORT`, `E2E_WEB_PORT` if 55498, 3100 or 5273 are taken (a leftover container of an interrupted run is replaced automatically). Tests run serially, without retries, against the synthetic demo data (seller 103 has 31 customers; the manager sees 250); failure traces, screenshots and the HTML report go to `apps/web/e2e/test-results` and `apps/web/e2e/playwright-report` (git-ignored).

## Seller sessions (AUTH-5, AUTH-6)

Sellers sign in through the directory verifier (AUTH-5), which does not exist in the throwaway stack and is not faked. The seller scenarios therefore open the session through a fixture (`support/session.ts`, AUTH-6 option c): it links the seeded seller account to a synthetic directory user id and inserts a `session` row (SHA-256 token hash, 8 h) directly in the throwaway Postgres container, then hands the plain token to the browser as the `sf_session` cookie. No HTTP endpoint is added to the product and nothing reaches production code paths; the fixture only reaches a database it started itself. The manager keeps the local username/password form login, which also covers the login screen scenarios.
